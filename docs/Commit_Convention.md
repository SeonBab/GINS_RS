# 커밋 메시지 규칙

이 프로젝트의 커밋 메시지는 변경 목적을 일관되게 파악할 수 있도록 다음 형식을 사용한다.

## 기본 형식

```text
type(scope): 변경 요약

필요한 경우 변경 내용과 이유를 작성한다.
```

- `type`은 변경의 종류를 나타낸다.
- `scope`는 변경 대상을 나타내며, 대상이 명확하거나 프로젝트 전체에 해당하면 생략할 수 있다.
- 제목만으로 충분한 단순 변경은 본문을 생략할 수 있다.

## Type

| Type | 기준 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | 캐릭터 대시 기능 추가 |
| `fix` | 버그 수정 | 충돌 후 중복 피해 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 | 입력 처리 책임 분리 |
| `chore` | 저장소 설정, 파일 정리 등 관리 작업 | `.gitignore` 규칙 정리 |
| `build` | 빌드 설정 또는 의존성 변경 | 모듈 의존성 추가 |
| `docs` | 문서만 변경 | 프로젝트 실행 방법 추가 |
| `test` | 테스트 추가 또는 수정 | 캐릭터 이동 테스트 추가 |
| `style` | 동작에 영향 없는 코드 서식 변경 | 들여쓰기와 공백 정리 |
| `perf` | 성능 개선 | Tick 연산 최적화 |

## Scope

`scope`에는 변경된 시스템, 기능 또는 저장소 영역의 이름을 사용한다.

```text
player
projectile
input
ui
gins
repo
```

- 프로젝트 전체의 저장소 설정은 `repo`를 사용한다.
- Unreal 모듈이나 주요 시스템은 해당 이름을 소문자로 작성한다.
- 여러 영역에 걸친 변경으로 하나의 대상을 고르기 어렵다면 `scope`를 생략한다.

## 작성 원칙

1. 제목은 변경 결과가 드러나도록 간결하게 작성한다.
2. 제목 끝에는 마침표를 붙이지 않는다.
3. 하나의 커밋에는 하나의 논리적 변경만 포함한다.
4. 본문에는 구현 과정의 나열보다 무엇을 왜 변경했는지 작성한다.
5. 호환성을 깨는 변경은 본문 또는 푸터에 `BREAKING CHANGE:`로 명시한다.
6. 관련 이슈가 있다면 푸터에 `Refs: #이슈번호` 또는 `Closes: #이슈번호`를 작성한다.

## 예시

### 제목만 작성하는 경우

```text
feat(player): 대시 기능 추가
```

```text
fix(projectile): 충돌 후 중복 피해 수정
```

```text
chore(repo): .gitignore 규칙 정리
```

### 본문을 함께 작성하는 경우

```text
refactor(input): 입력 처리 책임 분리

- Player 클래스에서 입력 바인딩 로직 분리
- 입력 변경이 캐릭터 동작 코드에 미치는 영향 축소
```

```text
build(gins): Enhanced Input 모듈 의존성 추가

- GINS.Build.cs에 EnhancedInput 모듈 추가
- 캐릭터 입력 시스템에서 모듈 API를 사용할 수 있도록 설정
```
